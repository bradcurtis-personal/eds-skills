# Security

**Trust boundary:** None -- this skill reads its declared inputs and writes only its own generated output files (new skill folders under `/skills/<name>/`). It does not mutate shared config, execute arbitrary code, open network ports, or cross any other trust boundary.

**Dependencies:** `main.py` needs only the Python standard library. `test.py` additionally requires PyYAML (`import yaml`), a test-time dependency pinned in the repo's `requirements.txt` and installed by the `skill-pr-check` workflow. `main.py` (generator and `--audit`) uses PyYAML to parse `SKILL.md` frontmatter when it is importable and falls back to a stdlib parser of single-line plain, single-quoted and double-quoted scalars when it is not (a strict subset of YAML: it never accepts a value `yaml.safe_load` would read differently). The generator and the audit of the repo's skills run without PyYAML; an audit without it reports a stale frontmatter, naming PyYAML, for any `SKILL.md` in another form (block or multi-line values, flow collections, anchors and so on). The generated `test.py` has its own stricter fallback, which accepts only a double-quoted `description:`.

The one action that touches a shared, durable surface -- writing a skill's entry to Notion during the documentation pass -- happens conversationally, outside `main.py`, only after explicit user confirmation of the drafted content (see README.md's "Documentation pass" section). `main.py` itself never reaches outside the local filesystem.
